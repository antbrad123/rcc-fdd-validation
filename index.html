Operator handbook

Proving a fault rule actually fires

A fault detection rule that has never been provoked is a guess. This is how we drive a BMS point on purpose, watch what the platform does with it, and put the point back where we found it.

Why we do this

When an FDD is built and enabled, all we really know is that it exists. We do not know whether it is watching the right point, whether its threshold is reachable in the real world, or whether the alarm it raises lands on the right asset. Validation closes that gap. We create the fault condition deliberately, then check the platform notices.

The cost of skipping this is quiet. Nothing breaks. The rule simply never fires, and a year later someone asks why an obvious fault was never picked up. Every rule in the register has either been proved or is waiting to be — there is no third category.

The point you drive is live plant

Everything here happens on a working building with people in it. A driven point is a real instruction to real equipment. Nothing in this handbook is worth a comfort complaint, a frozen coil, or a plant trip — if a test starts to affect the space, release the point and write up what you saw.

The five rules

  1. 01
    Record the normal value before you touch itYou cannot restore what you did not write down. The tracker holds the expected normal for every point, but the value on the day is what matters.
  2. 02
    Drive one point at a timeTwo overrides at once means you cannot tell which one the rule responded to. If the pattern genuinely needs two, note that explicitly in the result.
  3. 03
    Hold longer than the rule averages overMost rules filter over a window. A short push proves nothing and reads as a failure when it was a bad test.
  4. 04
    Restore before you write upRelease the point first, confirm the fault clears, then record the result. The write-up can wait; the plant cannot.
  5. 05
    Blocked is not FailedFailed means it was tested and the rule did not work. Blocked means it could not be tested at all. Mixing them makes the coverage figure meaningless.

How a test moves through the register

Not started is every rule as built. Scheduled means an access window is agreed and the point is confirmed writable. In test means the point is driven right now — this is the only status that puts an entry on the override ledger at the top of the screen. Passed and Failed both mean the test happened; only the outcome differs. Blocked parks it with a reason.

A rule that fails goes back to Not started once the engineer has revised it, and the retest count goes up by one. That count is the useful number over time — a pattern that needs three attempts across the estate is telling you the rule template itself is wrong, not that individual builds were sloppy.

The override ledger

The amber strip at the top of the screen lists every point currently driven and how long it has been that way. It is deliberately impossible to ignore. Anything sitting there over four hours turns red, because a forgotten override is worse than the fault it was meant to prove — it hides the real condition and it can be left behind at the end of a shift.

The strip disappears entirely when nothing is driven. An empty ledger is the state you hand over in.

When the FDD does not fire

Before recording a failure, work through the ordinary causes. Was the point actually accepted by the BMS, or did the write silently fail? Did you hold long enough for the rule's own averaging window? Is the asset in a mode the rule excludes, such as unoccupied or off? Does the rule depend on a second point that is not in the state it needs?

If all four check out and the rule still does not fire, that is a genuine failure and worth writing up in detail. Note the exact point, the value you drove it to, how long you held it, and what you expected. An engineer can act on that. "Didn't work" gives them nothing.
